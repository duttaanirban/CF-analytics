# CausalLens — User Analytics Application

A full-stack application that records webpage interactions and displays
visitor sessions, ordered event journeys, and page click maps.

Built for the CausalFunnel Full Stack Engineer assignment.

## Features

- Standalone JavaScript tracker installed through a script tag
- Automatic page-view and click tracking
- Browser identifier persisted in localStorage
- MongoDB event storage with request validation
- Session listing with event, page-view, and click counts
- Chronological session journeys
- Page selection and normalized click-position visualization
- Loading, empty, and error states
- Responsive dashboard and interactive demo storefront

## Tech Stack

- Frontend: React, Vite, JavaScript, CSS
- Backend: Node.js, Express
- Database: MongoDB Atlas, Mongoose
- Validation: Zod

## Local Setup

Prerequisites:
- Node.js compatible with the installed Vite version
- npm
- MongoDB Atlas connection string or a local MongoDB instance

### Backend

```bash
cd server
npm ci
```

Create `server/.env` using `server/.env.example`:

```env
PORT=5000
CLIENT_ORIGIN=http://localhost:5173
MONGODB_URI=YOUR_MONGODB_CONNECTION_STRING
```

For Atlas, configure a database user and allow the backend's IP address.

```bash
npm run dev
```

Health check: http://localhost:5000/api/health

### Frontend

In another terminal:

```bash
cd client
npm ci
```

Create `client/.env` using `client/.env.example`:

```env
VITE_API_URL=http://localhost:5000/api
```

```bash
npm run dev
```

Dashboard: http://localhost:5173  
Demo storefront: http://localhost:5173/demo.html

Use the demo, then click "Refresh data" on the dashboard.

## Tracker Integration

Add the script to a webpage:

```html
<script
  src="http://localhost:5173/tracker.js"
  data-endpoint="http://localhost:5000/api/events"
  defer
></script>
```

For hosting, replace these URLs with the deployed frontend and backend URLs.
The backend must allow the tracked webpage's origin through its CORS configuration.

The included demo uses a tracker configuration file generated automatically
by the frontend development and build commands.

## Event Format

```json
{
  "session_id": "browser-generated-uuid",
  "event_type": "click",
  "page_url": "http://localhost:5173/demo.html",
  "timestamp": "2026-10-13T06:00:00.000Z",
  "x": 350,
  "y": 420,
  "viewport_width": 1440,
  "viewport_height": 900,
  "document_width": 1440,
  "document_height": 1600
}
```

Click events require `x` and `y`. Page-view events do not.

`timestamp` represents the browser event time.
`received_at` is generated by the database layer when the event is stored.

## API Endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/events` | Validate and store an event |
| GET | `/api/sessions` | List sessions with aggregated counts |
| GET | `/api/sessions/:sessionId/events` | Fetch an ordered session journey |
| GET | `/api/pages` | List tracked pages with counts |
| GET | `/api/heatmap?pageUrl=ENCODED_URL` | Fetch clicks for a page |
| GET | `/api/health` | Check API and database availability |

Invalid event payloads return HTTP 400.
Unknown sessions return HTTP 404.

## Click Map

Click coordinates are document-relative, captured using `pageX` and `pageY`.

Each click is plotted as:

- Horizontal position: `x / document_width`
- Vertical position: `y / document_height`

The visualization is a normalized document grid, not a screenshot overlay.
It combines relative page positions across document sizes and does not
guarantee that clicks correspond to the same element across responsive layouts.

Clicks with missing dimensions or out-of-bounds coordinates are excluded
from the visualization and reported in the interface.

## Assumptions and Trade-offs

- The session identifier persists in localStorage across visits and tabs.
  It is a persistent browser identifier rather than an inactivity-based session.
- Clearing browser storage creates a new identifier.
- When storage is unavailable, an identifier is created for the current page load.
- A page view is recorded on each full page load. SPA route-change tracking
  is outside the current implementation.
- Page URLs are grouped exactly, including query strings and fragments.
- Event order uses browser timestamps, with MongoDB IDs as a tie-breaker.
  Browser clock accuracy can affect ordering.
- Tracking failures do not interrupt the demo webpage.
- Events are sent individually, without batching, retries, or deduplication.
- Read APIs return all matching records. Pagination is a future improvement.
- The demo has no authentication or rate limiting. CORS controls browser
  access but is not authentication.
- The tracker stores page URLs and interaction metadata. Sensitive values
  should not be placed in tracked URLs.

## Database Indexes

- `session_id + timestamp` for session journeys
- `page_url + event_type + timestamp` for page click queries

Session counts are aggregated from stored events instead of maintained
in a separate collection.

## Verification

```bash
cd client
npm run build
npm run lint
```

Manual checks:

1. Opening the demo records a page view.
2. Clicking records coordinates and the page URL.
3. Reloading retains the browser identifier.
4. A separate browser profile creates another identifier.
5. Session counts match stored events.
6. Session journeys display events chronologically.
7. Page selection displays the corresponding clicks.
8. A click without required coordinates is rejected.
9. Backend failures produce a dashboard error state.

## Deployment Configuration

Backend environment variables:
- `PORT`: supplied by the host when applicable
- `MONGODB_URI`: database connection string
- `CLIENT_ORIGIN`: deployed frontend origin, without a trailing slash

Frontend build environment variable:
- `VITE_API_URL`: deployed backend URL followed by `/api`

Frontend build command: `npm run build`
Frontend output directory: `dist`
Backend start command: `npm start`

The frontend must be rebuilt after changing `VITE_API_URL`.
